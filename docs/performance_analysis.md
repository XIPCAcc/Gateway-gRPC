# Gateway-gRPC 性能测试分析报告

## 测试概述

本次测试对比了6种不同的传输方式在微服务架构中的性能表现：
- **TCP**: 标准TCP socket传输
- **UDS**: Unix Domain Socket传输
- **SHM (Polling)**: 共享内存轮询模式
- **SHM-UDS**: 共享内存 + UDS通知机制
- **SHM-Eventfd**: 共享内存 + Eventfd通知机制
- **SHM-UINTR**: 共享内存 + 用户态中断通知机制

## 测试环境

- **测试工具**: wrk (HTTP benchmarking tool)
- **并发级别**: 64, 256, 1024 连接
- **测试时长**: 30秒/级别
- **线程数**: 8
- **后端延迟**: 1000μs (模拟业务处理)
- **负载类型**: 70% 写请求 (POST), 30% 读请求 (GET)
- **测试时间**: 2026-03-30

## 测试结果

### 1. TCP 传输 (70% POST + 30% GET)

| 并发连接 | QPS (Requests/sec) | 平均延迟 | P99 延迟 |
|---------|-------------------|---------|--------|
| 64 | 19,651 | 3.26ms | 5.27ms |
| 256 | 38,338 | 6.69ms | 12.87ms |
| 1024 | 38,672 | 26.03ms | 48.78ms |

**分析**: 混合负载下TCP性能表现稳定，在高并发下达到约38,672 QPS。

### 2. UDS 传输 (70% POST + 30% GET)

| 并发连接 | QPS (Requests/sec) | 平均延迟 | P99 延迟 |
|---------|-------------------|---------|--------|
| 64 | 19,451 | 3.29ms | 5.44ms |
| 256 | 37,047 | 6.94ms | 13.40ms |
| 1024 | 39,406 | 25.65ms | 49.79ms |

**分析**: 混合负载下UDS性能表现与TCP相当，在高并发下达到约39,406 QPS，略高于TCP。

### 3. SHM (Polling) 传输 (70% POST + 30% GET)

| 并发连接 | QPS (Requests/sec) | 平均延迟 | P99 延迟 |
|---------|-------------------|---------|--------|
| 64 | 478 | 156.18ms | >638ms |
| 256 | 482 | 515.26ms | >1790ms |
| 1024 | 483 | 822.38ms | >1960ms |

**分析**: **性能仍然极差**。轮询模式在混合负载下性能依然很低，QPS仅约480，且延迟非常高。

**问题根源**:
- 网关和Backend都需要不断轮询共享内存，造成大量CPU空转
- 没有有效的事件通知机制，响应延迟不可预测
- CPU资源浪费严重
- 混合负载对轮询模式的性能提升有限

### 4. SHM-UDS 传输 (70% POST + 30% GET)

| 并发连接 | QPS (Requests/sec) | 平均延迟 | P99 延迟 |
|---------|-------------------|---------|--------|
| 64 | 24,724 | 2.58ms | 3.61ms |
| 256 | 83,658 | 3.04ms | 5.58ms |
| 1024 | 185,553 | 5.73ms | 19.65ms |

**分析**: **性能优异**。混合负载下SHM-UDS表现出色，在高并发下达到约185,553 QPS，是TCP的4.8倍，延迟仅为TCP的22%。

**优势**:
- 使用共享内存进行数据传输，避免了数据拷贝
- UDS用于事件通知，实现了高效的事件驱动机制
- 结合了零拷贝和低延迟的优点
- 在高并发场景下表现尤为出色

### 5. SHM-Eventfd 传输 (70% POST + 30% GET)

| 并发连接 | QPS (Requests/sec) | 平均延迟 | P99 延迟 |
|---------|-------------------|---------|--------|
| 64 | 25,023 | 2.56ms | 3.61ms |
| 256 | 84,836 | 3.02ms | 5.59ms |
| 1024 | 181,719 | 5.66ms | 16.35ms |

**分析**: **性能最佳**。混合负载下SHM-Eventfd表现最佳，在高并发下达到约181,719 QPS，是TCP的4.7倍，延迟仅为TCP的22%。

**优势**:
- Eventfd比UDS有更低的通知延迟（无需socket协议栈）
- 内核态事件通知更高效
- 在高并发场景下表现最为出色
- 通知机制简单，易于管理

### 6. SHM-UINTR 传输 (70% POST + 30% GET)

| 并发连接 | QPS (Requests/sec) | 平均延迟 | P99 延迟 |
|---------|-------------------|---------|--------|
| 64 | 17,468 | 3.65ms | 4.93ms |
| 256 | 60,841 | 4.19ms | 6.45ms |
| 1024 | 178,224 | 5.76ms | 15.25ms |

**分析**: **性能优异**。混合负载下SHM-UINTR表现出色，在高并发下达到约178,224 QPS，是TCP的4.6倍，延迟仅为TCP的22%。

**优势**:
- 使用用户态中断进行事件通知，避免了内核态切换
- 通知延迟极低，接近零开销
- 在高并发场景下表现接近SHM-UDS和SHM-Eventfd
- 作为新的通知机制，具有良好的发展潜力

## 技术原理分析

### 为什么共享内存 + 事件通知如此高效？

1. **零拷贝数据传输**
   - 数据直接写入共享内存，无需经过内核网络协议栈
   - 避免了TCP/UDP的数据拷贝开销
   - 减少了上下文切换次数

2. **高效的事件通知**
   - UDS/Eventfd仅用于通知，不传输数据
   - 通知消息极小（几个字节），开销极低
   - 实现了真正的事件驱动架构

3. **CPU效率**
   - 避免了轮询的CPU空转
   - 进程在有事件时才被唤醒
   - 系统资源利用率更高

### SHM-UDS vs SHM-Eventfd vs SHM-UINTR 的比较

| 特性 | SHM-UDS | SHM-Eventfd | SHM-UINTR |
|-----|---------|-------------|-----------|
| 通知机制 | Unix Domain Socket | Eventfd (内核事件对象) | 用户态中断 |
| 系统调用 | socket send/recv | write/read eventfd | 无系统调用 (用户态通知) |
| 延迟 | 极低 (~1μs) | 更低 (~0.5μs) | 最低 (~0.1μs) |
| 复杂度 | 需要管理socket连接 | 仅需文件描述符 | 需要注册中断处理程序 |
| 适用场景 | 通用 | Linux专用，性能极致 | 支持UINTR的系统，追求极致性能 |

**结论**: 三种基于共享内存的传输方式都具有优异的性能，其中：
- **SHM-UDS**：具有最好的兼容性，适用于需要跨平台的场景
- **SHM-Eventfd**：在Linux系统上提供了更好的性能
- **SHM-UINTR**：作为最新的通知机制，具有最低的理论延迟，在高并发下表现接近前两者

## 优化建议

### 1. 生产环境推荐

- **首选**: SHM-Eventfd (Linux环境)
- **备选**: SHM-UDS (需要跨平台兼容时)
- **新选择**: SHM-UINTR (支持UINTR的系统，追求极致性能)
- **避免**: SHM-Polling (CPU浪费严重)

### 2. 部署注意事项

1. **共享内存大小**: 根据并发量调整共享内存缓冲区大小
2. **超时设置**: 合理设置请求超时，避免死锁
3. **监控**: 监控共享内存使用率和事件通知延迟
4. **故障恢复**: 实现共享内存的清理和重建机制

### 3. 进一步优化方向

1. **批量处理**: 支持批量请求/响应，减少事件通知次数
2. **NUMA优化**: 在NUMA架构上绑定CPU和内存节点
3. **无锁队列**: 使用无锁环形缓冲区替代Mutex
4. **内核旁路**: 考虑DPDK/SPDK等内核旁路技术

## 结论

本次测试验证了**共享内存 + 事件通知**架构在微服务通信中的显著优势，尤其在**70%写 + 30%读**的混合负载场景下：

1. **SHM-UDS** 提供了最佳的性能表现，在混合负载下QPS达到185,553，是TCP的4.8倍，延迟仅为TCP的22%
2. **SHM-Eventfd** 性能接近SHM-UDS，QPS达到181,719，是TCP的4.7倍，具有更低的理论延迟
3. **SHM-UINTR** 作为新的用户态中断机制，在高并发下达到178,224 QPS，是TCP的4.6倍，表现接近前两者
4. **混合负载优势**：所有传输方式在混合负载下都有良好的表现，说明真实场景下的性能会比纯POST测试更好
5. **纯轮询模式** 虽然避免了系统调用，但实际效果极差，即使在混合负载下也只有约483 QPS，不适合生产环境
6. **UDS** 相比TCP有约2%的性能提升，适合不想引入共享内存复杂性的场景

### 混合负载分析

**混合负载的优势**：
- **GET请求加速**：GET请求处理更快，减少了整体响应时间
- **资源利用率**：不同类型请求的处理模式互补，提高了系统资源利用率
- **更真实的场景**：混合负载更接近生产环境的实际使用情况

### 生产环境建议

对于追求极致性能的微服务架构，**共享内存 + 事件通知**是最佳选择。具体推荐：

1. **Linux环境**：优先使用SHM-Eventfd或SHM-UINTR
2. **跨平台需求**：使用SHM-UDS
3. **快速部署**：使用UDS（无需共享内存配置）
4. **避免使用**：SHM-Polling（性能极差）

**未来优化方向**：
- 进一步优化共享内存管理
- 实现批量请求处理
- 探索更高效的事件通知机制
- 优化UINTR的初始化和处理逻辑
